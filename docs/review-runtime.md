# ConsistenCy Review Runtime & Context VM

This document explains the execution lifecycle of a code review run in ConsistenCy v3, detailing how Context VM pages, deterministic evidence, and agent control blocks collaborate to produce evidence-grounded findings.

---

## 1. Review Execution Flow

```text
Repository ──▶ ReviewJob ──▶ Kernel Run ──▶ Agents (ACBs) ──▶ EvidenceStore ──▶ ReviewReport ──▶ Findings
```

1. **Job Initialization**: A review is triggered either locally (via Desktop/API trigger) or remotely (via GitHub pull request webhook).
2. **Snapshot Pinning**: A `RepositorySnapshot` is created and strictly pinned to the immutable `headSha` and `baseSha`.
3. **Run Activation**: The Kernel registers and activates a `Run` object (`run_<id>`).
4. **Deterministic Analysis**: Grounding evidence is generated by deterministic analyzers (Tree-sitter AST queries, secret detectors, style analyzers, Python stdio engine) and ingested into the `EvidenceStore`.
5. **Context VM Base Image**: An initial `ContextImage` is formed by allocating immutable `ContextPage`s for the review task, diff text, and relevant source files.
6. **Agent Scheduling**: The `KernelScheduler` admits the Supervisor (Planner) and specialized review agents under strict priority and concurrency constraints.
7. **Agent Execution & COW Forks**: Child agents receive Copy-On-Write (COW) forks of the parent `ContextImage`, attaching specialized context pages without copying underlying text buffers.
8. **Syscall-Mediated LLM Calls**: LLM queries (`llm.invoke`) are authorized by `CapabilityBroker` and executed through trusted Ring 1 drivers.
9. **Evidence Grounding & Synthesis**: Agent findings reference verified `evidenceIds`. Findings without verified evidence are marked with lower confidence or hypothesis status.
10. **Report Persistence**: The resulting `ReviewReport` is persisted in SQLite, and irreversible mutations (such as posting GitHub comments) are queued to the durable `CommitCoordinator` outbox.

## 2. Context VM Architecture

The Context VM (`@consistency/kernel`) treats prompt and context memory as structured, addressable pages rather than raw concatenated strings:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            Context VM Page Table                            │
├────────────┬─────────────┬──────────────┬───────────────┬───────────────────┤
│  Page ID   │    Kind     │ Content Hash │   Residency   │ Estimated Tokens  │
├────────────┼─────────────┼──────────────┼───────────────┼───────────────────┤
│ page_001   │ policy      │ sha256_...   │ PINNED        │ 120               │
│ page_002   │ diff        │ sha256_...   │ PINNED        │ 850               │
│ page_003   │ source      │ sha256_...   │ HOT           │ 1,420             │
│ page_004   │ evidence    │ sha256_...   │ HOT           │ 340               │
│ page_005   │ summary     │ sha256_...   │ COLD          │ 210               │
└────────────┴─────────────┴──────────────┴───────────────┴───────────────────┘
```

### 2.1 Context Page Primitives
- **`ContextPage`**: Immutable text chunk identified by its SHA-256 `contentHash`. Pages are shared across agent images without duplication.
- **Page Kinds**: `policy`, `task`, `diff`, `source`, `ast`, `symbol`, `evidence`, `tool-result`, `memory`, `summary`.
- **Deterministic Precedence**: During context rendering, pages are ordered deterministically by kind precedence (`policy` first, `summary` last) and page ID.
- **`ContextImage`**: An overlay referencing a collection of pages with specific residency states:
  - `PINNED`: Always included in the rendered working set.
  - `HOT`: Active in current agent memory and included in token calculations.
  - `COLD`: Retained in image metadata but excluded from active prompts.
  - `EVICTED`: Marked as discarded when token budgets are exceeded.
- **`WorkingSet`**: The computed subset of `PINNED` and `HOT` pages projected into a rendered prompt with deterministic token estimation.
- **Copy-On-Write (COW) Forking**: When an agent spawns child subagents, `ContextManager.fork()` clones the page-table references in $O(N)$ references without copying text data.

## 3. Evidence Engine & Provenance

Findings in ConsistenCy are not arbitrary LLM prose. Every finding must be linked to deterministic evidence records:

### 3.1 Evidence Provenance
Every evidence record in `EvidenceStore` records:
- `repository`: Canonical repository name (e.g. `owner/repo`).
- `sha`: Exact Git commit SHA (never floating branch names).
- `analyzer`: The analyzer engine identifier (e.g. `ast.treesitter`, `sast.secrets`, `python.engine`).
- `analyzerVersion`: Exact version of the analyzer implementation.

### 3.2 Canonical Fingerprinting
The fingerprint is computed via SHA-256 over a canonical JSON tuple:
$$\text{Fingerprint} = \text{SHA256}(\text{canonicalJson}([ \text{source}, \text{ruleId}, \text{path}, \text{startLine}, \text{endLine}, \text{confidence}, \text{payload}, \text{repository}, \text{sha}, \text{analyzer}, \text{analyzerVersion} ]))$$

This guarantees that identical findings produced on different Git commits have distinct cryptographic identities.

## 4. Runtime Observability & Task Manager

Review runs can be inspected live via the Web/Desktop Runtime view or via HTTP endpoints:
- `GET /api/runtime/runs`: List of active and recent runs.
- `GET /api/runtime/runs/:runId`: Full runtime snapshot including Agent Control Blocks, process tree hierarchy, scheduler states (`WAIT_LLM`, `WAIT_TOOL`), Context VM page distribution, token consumption, and sanitized capability fingerprints.
